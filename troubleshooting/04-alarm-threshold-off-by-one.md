# Incident 04 — CloudWatch alarm never fires despite the app being down

## Context
While testing the monitoring setup, I took the app down to confirm the
`UnHealthyHostCount` alarm would fire. The health checks were clearly failing
(logs full of 503s, the ALB DNS returned "Internal Server Error"), but the alarm
stayed in **OK / Insufficient data** and never entered ALARM.

## Symptom
- App logs showed continuous health check failures:
  `Health check failed: ... "GET /health HTTP/1.1" 503`
- Browsing the ALB DNS name returned **500 Internal Server Error**.
- The `UnHealthyHostCount` metric graph rose to and held at **1**.
- Yet the alarm state never changed to **In alarm**.

## What the symptom told me
The metric was clearly reporting the unhealthy host (value = 1 on the graph), so
this wasn't a "no data" problem — the alarm was *receiving* data but *deciding* not
to fire. That points at the alarm's threshold/condition, not the metric.

## Root cause
The alarm condition was:
```
UnHealthyHostCount > 1 for 1 datapoints within 1 minute
```
The threshold was **strictly greater than 1**. But this environment has a **single
instance**, so when it becomes unhealthy, `UnHealthyHostCount` equals exactly **1**.
Since `1 > 1` is false, the condition never breached and the alarm never fired. It
was effectively requiring *two* unhealthy hosts before alerting — impossible with one
target.

An off-by-one error in the threshold: `>` should have been `>=`.

## Fix
Edited the alarm and changed the condition from **Greater than (`>`) 1** to
**Greater/Equal (`>=`) 1**. Within a minute — with the target still unhealthy — the
alarm transitioned to **In alarm** and the SNS email was delivered.

## Related finding — the 5XX alarm
The `HTTPCode_ELB_5XX_Count` alarm also never fired. The 500 error seen in the browser
was generated by the **application**, which is recorded under
`HTTPCode_Target_5XX_Count`, not `HTTPCode_ELB_5XX_Count` (the latter counts errors the
load balancer itself returns, e.g. a 503 when there are no healthy targets). Watching
the ELB metric meant app-level 500s were invisible to it. Fix: alarm on
`HTTPCode_Target_5XX_Count` to catch application errors (and optionally keep an ELB 5XX
alarm for load-balancer-level failures).

## Prevention / what I'd tell a customer
- For count metrics where **any** nonzero value is bad, use `>= 1`, never `> 1`. With
  `> 1` on a single-target group, the alarm can never fire because the count maxes at 1.
- Always **test that an alarm actually fires** by inducing the failure — a configured
  alarm is not a working alarm until you've seen it transition to ALARM. This bug was
  only visible because I tested it.
- Know which metric reflects which failure: `UnHealthyHostCount` (target health, state-
  based), `HTTPCode_Target_5XX_Count` (app errors), `HTTPCode_ELB_5XX_Count` (load
  balancer errors). Alarming on the wrong one gives false confidence.
